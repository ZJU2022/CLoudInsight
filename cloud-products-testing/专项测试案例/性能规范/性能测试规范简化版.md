# 性能测试规范

## 性能测试基本概念

### 1.1 了解性能测试场景  
统一概念，只有性能测试，没有压力测试，负载测试，稳定压力测试等等，这些都是性能测试的一个场景  

| 场景类型         | 作用                                                                                                     |
|------------------|----------------------------------------------------------------------------------------------------------|
| 基准性能场景     | 确定系统在正常运行环境下的性能水平，作为性能优化的参考。如云主机基准性能测试，测试主机正常情况下的CPU，网络，磁盘IO等 |
| 容量性能场景     | 确定系统的极限容量，即系统在承载压力过大时会出现的性能问题或故障。提供容量规划和资源分配的依据                 |
| 稳定性性能场景   | 在长时间压力测试下，观察系统的性能表现，分析瓶颈并且调优                                                   |
| 异常性能场景     | 先定义异常，根据真实业务场景和系统架构确定异常（如挂主机，挂DB，网络异常，熔断），验证系统的健壮性           |

**AB机制：**  
ApacheBench（ab）工具在设置并发连接数时，是在测试开始时立即创建并发连接，而不是慢慢增加的。这意味着一旦测试开始，ab就会尽快建立指定数量的并发连接，然后在整个测试期间保持这个水平。AB的机制可以大致分为以下几个步骤：  
1. 创建并发连接：在测试开始时，AB会立即创建指定数量的并发连接  
2. 发送请求：一旦建立了并发连接，AB就会开始向服务器发送请求  
3. 等待响应：AB会等待服务器的响应，并记录下每个请求的响应时间  
4. 处理响应：收到服务器响应后，AB会记录响应的相关信息，如响应代码、响应大小等  
5. 统计结果：在测试结束后，AB会汇总所有请求的结果，并生成报告

### 1.3 了解性能测试指标  

| 指标名称     | 具体含义                                                                                                                                                                  |
|--------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| TPS          | 每秒事务数，测试人员定义事务。一个接口可以事务，多个接口也可以是事务，一个流程也可以是事务，事务代表一个完整的功能                                                           |
| QPS          | 每秒查询数，Mysql中指每秒sql数                                                                                                                                            |
| RT           | 接口响应时间（响应时间），分为前端展现时间和系统响应时间两部分。软件的性能测试一般更关注服务器端                                                                           |
| 系统吞吐量   | 单位时间业务处理数量，是最能直接体现软件系统负载承受能力的指标                                                                                                             |
| 资源利用率   | CPU，内存，磁盘，网络                                                                                                                                                     |
| 并发用户数   | 业务层面的并发用户数，指的是实际使用系统的用户总数。但是，单靠这个指标并不能反映系统实际承载的压力，我们还要结合用户行为模型才能得到系统实际承载的压力。后端服务器层面的并发用户数，指的是"同时向服务器发送请求的数量"，直接反映了系统实际承载的压力 |

### 1.4 了解常见负载策略  
递增测试在性能中必不可少（基准性能场景也好，容量性能场景也好，都是需要递增的），非常不推荐直接就上了几百几千线程做压力（请这不是个正常的场景，除了秒杀场景）。在一般的性能场景中，递增都是必不可少的过程。同时，递增的过程，也要是连续的，而不是100线程、200线程、300线程这样断开执行场景，这样是不合理的。

### 1.5 了解性能项目分类  

| 项目类型                 | 特点                                                                                 |
|--------------------------|--------------------------------------------------------------------------------------|
| 新系统性能测试类         | 一般会要求测试出系统的最大容量，不然上线心里没底                                       |
| 旧系统新版本性能测试类   | 一般都是和旧版本对比，只要性能不下降就可以根据历史数据推算容量，对调优要求一般都不大     |
| 新系统性能测试优化类     | 不仅要测试出最大容量，还要求调优到最好                                                 |

## 性能测试方案模板  

| 步骤                   | 详细描述                                                                                                 |
|------------------------|----------------------------------------------------------------------------------------------------------|
| 1. 确定性能测试模型    | 将真实业务场景抽象为性能测试场景，确保测试反映真实的使用情况<br>eg：业务比例设置，30%读，70%写               |
| 2. 确定性能测试场景    | 明确自己需要的数据<br>（eg：最大吞吐量，最小吞吐量，99.9%的完整请求所经历的时间，索引的每个任务的响应错误率，所有主分片索引累积时间总和等等） |
| 3. 确定性能测试方案    | 明确测试环境<br>明确测试数据<br>明确性能指标<br>明确负载策略<br>明确准入准出风险（eg：网络问题，影响线上客户） |
| 4. 确定监控方案        | 明确需要监控的性能指标（如响应时间、吞吐量等）<br>明确监控工具（eg：mysql_exporter + Prometheus + Grafana） |
| 5. 执行                | 工具：了解性能测试工具<br>代码：-                                                                        |
| 6. 根据性能报告决定    | 了解性能分析思路                                                                                       |

### 使用说明  
1. 基准性能场景适用于新系统上线前的性能评估  
2. 容量性能场景和稳定性性能场景建议每月执行一次  
3. 异常性能场景应在每次架构变更后执行  
4. 所有测试报告必须包含基准测试结果作为参照  

### 注意事项  
- 递增测试策略必须应用于所有非秒杀场景  
- AB工具使用前必须验证连接机制是否适合当前场景  
- 监控方案必须覆盖从应用层到底层资源的所有关键指标  
- 性能报告中必须明确区分服务器响应时间和前端渲染时间
